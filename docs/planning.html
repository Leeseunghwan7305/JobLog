01

서비스 개요

구직자가 동시에 지원하는 여러 공고의 진행 상태를 놓치지 않고 관리하도록 돕는다.

취업 준비 기간에는 보통 수십 개의 공고에 동시에 지원한다. 각 회사마다 전형 절차가 다르고(서류 → 코딩테스트 → 1차 면접 → 2차 면접 → 최종), 지원 시점과 발표 일정이 제각각이라 "지금 어디까지 진행됐는지"를 머릿속이나 엑셀로 관리하기 어렵다.

JobLog는 공고 링크 하나만 넣으면 AI가 회사·직무·전형 단계를 자동으로 추출해 카드로 만들고, 사용자는 각 전형의 상태(진행 중 / 합격 / 탈락 / 대기)만 클릭해 갱신하면 된다. 흩어진 지원 현황이 하나의 보드로 모인다.

엑셀로 관리하면?

회사가 늘어날수록 행이 복잡해지고, 전형 단계·일정을 매번 수기로 입력해야 한다.

머릿속으로 관리하면?

면접 일정이 겹치거나, 발표를 놓치거나, 어느 전형에서 떨어졌는지 기억이 섞인다.

TARGET

타깃 사용자

여러 기업에 동시 지원하는 신입·주니어 구직자, 이직 준비자. 특히 개발·IT 직군처럼 전형 단계가 많은 분야.

VALUE

핵심 가치

"입력 노동을 AI가 대신한다." 공고를 읽고 구조화하는 귀찮은 과정을 자동화하고, 사용자는 상태 추적에만 집중한다.

DIFF

차별점

단순 메모 앱이 아니라 공고 → 전형 구조 자동 파싱 + 단계별 상태 머신. 회사별로 다른 절차를 그대로 반영한다.

02

핵심 기능 (MVP)

v1 출시에 반드시 포함되는 기능. 그 외는 10. 로드맵의 후속 마일스톤으로 분리한다.

F1 · AUTH

카카오 소셜 로그인

별도 회원가입 없이 카카오 계정으로 로그인. 사용자별로 자신의 지원 현황만 조회·관리한다. (OAuth 2.0 + 서버 발급 JWT)

F2 · AI

공고 링크 → 자동 분석

입력창에 공고 링크만 붙여넣으면 스크래핑(Firecrawl)으로 본문을 수집하고 AI(Claude)가 회사명·직무·전형 단계·마감일을 추출해 지원 카드 초안을 만든다.

F3 · FALLBACK

붙여넣기 폴백 & 보정

링크 수집이 실패하거나 내용이 빈약하면 "공고 내용 붙여넣기" 창으로 자동 전환. AI가 잘못 뽑은 항목은 폼에서 바로 수정하고, 전형 단계도 추가·삭제·순서 변경할 수 있다.

F4 · TRACK

단계별 상태 관리

각 전형마다 대기 진행중 합격 탈락 상태를 지정. "서류 합격 / 1차 면접 진행 중"처럼 현재 위치가 한눈에 보인다.

F5 · BOARD

지원 현황 보드 & 대시보드

진행 상태별로 카드를 모아 보는 칸반/리스트 뷰와, 지원 수·진행 중·합격·탈락 통계를 보여주는 대시보드.

F6 · SCHEDULE

일정 · 마감 관리

전형별 예정일(면접일, 발표일, 마감일)을 기록하고 임박한 일정을 상단에 노출. (알림은 M4로 확장)

F7 · REVIEW M4 · best-effort

기업 후기 (잡플래닛)

지원 상세에서 회사명으로 잡플래닛의 공개 평점·요약을 참고용으로 표시하고, "자세히 보기"는 잡플래닛 페이지로 딥링크. 로그인·블러·ToS 제약으로 전체 후기 본문은 긁어오지 않는다.

03

사용자 플로우

공고를 발견한 순간부터 지원 카드가 보드에 올라가기까지의 핵심 경로.

1

카카오 로그인

카카오 계정으로 진입. 첫 로그인 시 사용자 계정이 자동 생성된다.

2

공고 링크 붙여넣기

메인 입력창에 공고 링크를 붙여넣고 "분석" 클릭. (안 될 때만 본문 붙여넣기)

3

자동 수집 & 추출

Firecrawl이 공고 본문을 수집하고 Claude가 회사·직무·전형 단계·마감일을 뽑아 카드 초안을 만든다.

4

확인 & 보정

틀린 부분만 수정하고 저장. 지원 카드가 확정된다.

5

상태 추적

전형이 진행될 때마다 단계 상태를 갱신하며 관리한다.

UX 원칙 행복 경로는 "링크만 붙여넣기"다. 링크 수집이 실패하면 본문 붙여넣기로 자동 폴백하고, AI 추출이 틀려도 4단계 보정이 받쳐주므로 어떤 공고든 결국 등록된다. AI·스크래핑은 "초안 생성기", 최종 권한은 사용자에게 있다.
04

채용 전형 파이프라인

전형은 회사마다 다르다. 그래서 고정 목록이 아니라 지원(Application)마다 단계(Stage) 배열을 따로 갖고, 각 단계는 독립된 상태를 가진다. 아래는 한 지원 카드의 상태 예시.

STAGE 01 서류 전형 합격
STAGE 02 코딩 테스트 합격
STAGE 03 1차 면접 진행중
STAGE 04 2차 면접 대기
STAGE 05 최종 발표 대기
가변 전형 단계 이름·개수는 자유다. 어떤 회사는 서류 → 1차 면접 → 2차 컬쳐핏 면접 → 처우협의, 어떤 회사는 서류 → 과제 → 임원면접이다. AI가 공고에서 실제 명칭을 그대로 뽑고, 사용자가 추가·삭제·순서변경·이름수정으로 보정한다.
STAGE STATUS

단계 상태 (StageStatus)

PENDING 아직 진행 전  ·  IN_PROGRESS 진행 중  ·  PASSED 통과  ·  FAILED 탈락

APPLICATION STATUS

지원 전체 상태 (파생값)

IN_PROGRESS 진행 중  ·  OFFER 최종 합격  ·  REJECTED 불합격  ·  CLOSED 지원 철회

전체 지원 상태는 각 단계 상태로부터 자동 계산한다. 하나라도 FAILED면 불합격, 마지막 단계가 PASSED면 최종 합격, 그 외엔 진행 중으로 본다.

06

데이터 모델

Prisma 스키마 초안. 핵심은 User 1 : N Application 1 : N Stage 구조와 변경 이력(StatusLog)이다.

prisma / schema.prisma
model User {
  id          String   @id @default(cuid())
  kakaoId     String   @unique   // 카카오 고유 식별자
  email       String?
  nickname    String
  profileImage String?
  applications Application[]
  createdAt   DateTime @default(now())
}

model Application {        // 하나의 지원(= 회사 하나)
  id          String   @id @default(cuid())
  user        User     @relation(fields: [userId], references: [id])
  userId      String
  companyName String              // 회사명 (AI 추출)
  position    String              // 직무
  jobUrl      String?             // 원본 공고 링크
  rawPosting  String?  @db.Text   // 붙여넣은 공고 원문
  location    String?
  employmentType String?          // 정규직/인턴 등
  deadline    DateTime?           // 지원 마감일
  status      AppStatus @default(IN_PROGRESS)
  memo        String?  @db.Text
  stages      Stage[]
  logs        StatusLog[]
  appliedAt   DateTime?
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  @@index([userId, status])
}

model Stage {              // 전형 단계 (서류/코테/면접…)
  id          String   @id @default(cuid())
  application Application @relation(fields: [applicationId], references: [id], onDelete: Cascade)
  applicationId String
  name        String              // "1차 면접"
  order       Int                 // 전형 순서
  status      StageStatus @default(PENDING)
  scheduledAt DateTime?           // 예정일(면접·발표)
  completedAt DateTime?

  @@index([applicationId, order])
}

model StatusLog {          // 상태 변경 이력
  id          String   @id @default(cuid())
  application Application @relation(fields: [applicationId], references: [id], onDelete: Cascade)
  applicationId String
  stageName   String
  fromStatus  String?
  toStatus    String
  createdAt   DateTime @default(now())
}

enum AppStatus   { IN_PROGRESS  OFFER  REJECTED  CLOSED }
enum StageStatus { PENDING  IN_PROGRESS  PASSED  FAILED }

// M4 — 기업 후기 캐시 (잡플래닛 재조회 비용·호출 절감용)
model CompanyReview {
  id          String   @id @default(cuid())
  companyName String   @unique
  rating      Float?              // 공개 평점
  summary     String?  @db.Text   // 요약 (전체 본문 저장 X)
  sourceUrl   String?             // 잡플래닛 딥링크
  fetchedAt   DateTime @default(now())
}
주의 기업 후기는 잡플래닛의 공개 평점·요약만 best-effort로 캐시하고 전체 후기 본문은 저장·스크래핑하지 않는다 (로그인·블러·ToS 제약). 자세히 보기는 잡플래닛으로 딥링크한다.
07

기술 스택

프론트와 백엔드를 분리한 구성. AI 파싱은 백엔드에서 Claude API로 처리해 키를 노출하지 않는다.

Frontend

  • Next.js (App Router)페이지·라우팅·SSR
  • TanStack Query서버 상태 캐싱·동기화
  • shadcn/ui + Tailwind컴포넌트·스타일링
  • TypeScript타입 안정성

Backend

  • NestJS모듈 기반 API 서버
  • Prisma ORM타입세이프 DB 접근
  • PostgreSQL관계형 데이터 저장
  • Passport (Kakao + JWT)인증·인가
  • Claude API공고 → 구조화 파싱

Infra

  • Vercel프론트 배포
  • Railway / RenderNest 서버 배포
  • Neon / Supabase관리형 PostgreSQL
  • GitHub ActionsCI (린트·테스트)
08

시스템 아키텍처

클라이언트는 Nest API와만 통신하고, 외부 연동(카카오·Claude)은 전부 서버 뒤에 둔다.

architecture / data flow
┌─────────────┐      ┌───────────────────────────┐      ┌────────────┐
│  Next.js    │ ──►  │        NestJS API         │ ──►  │ PostgreSQL │
│  (Vercel)   │ ◄──  │  Auth · Applications ·    │ ◄──  │  (Prisma)  │
│ React Query │      │  Stages · Parse · Reviews  │      └────────────┘
└─────────────┘      └──┬────────┬─────────┬──────┘
                  OAuth │   scrape │ parse   │ reviews
                        ▼        ▼         ▼         ▼
              [Kakao Login] [Firecrawl] [Claude API] [Jobplanet]
                           URL→본문    본문→JSON    평점·요약
                                       { company, position,   (best-effort
                                         stages[], deadline }   · 딥링크)
AI PARSING

파싱 파이프라인

① Firecrawl로 공고 링크 본문 수집(실패 시 붙여넣은 원문 사용) → ② Claude에 구조화 프롬프트(JSON 스키마 강제) 전달 → ③ 검증된 JSON을 Application/Stage 초안으로 변환 → ④ 프론트에 반환해 사용자가 보정. 수집과 이해를 분리해 수집 수단은 교체 가능.

SECURITY

인증 흐름

카카오 OAuth 콜백을 Nest가 받아 사용자 조회/생성 후 자체 JWT(access/refresh) 발급. 모든 /applications 요청은 JWT의 userId로 소유권을 검증한다.

09

API 설계

REST 기준 주요 엔드포인트. 모든 지원/전형 API는 인증 필수이며 본인 리소스만 접근 가능.

Method Path 설명
GET /auth/kakao/callback 카카오 OAuth 콜백 → JWT 발급
GET /auth/me 로그인한 사용자 정보 조회
POST /applications/parse 공고 링크 → Firecrawl 수집 + AI 추출 결과(초안) 반환 (링크 실패 시 body의 본문 사용)
POST /applications 보정된 초안으로 지원 카드 생성
GET /applications 내 지원 목록 (상태별 필터·정렬)
GET /applications/:id 지원 상세 (전형·일정·메모 포함)
PATCH /applications/:id 회사·직무·메모 등 수정
DELETE /applications/:id 지원 삭제
PATCH /applications/:id/stages/:stageId 전형 단계 상태·일정 갱신
GET /companies/reviews?name= 기업 후기(잡플래닛) 공개 평점·요약 조회 — best-effort, 캐시 (M4)
GET /dashboard/stats 지원 수·진행중·합격·탈락 통계
10

개발 로드맵

MVP를 최단 경로로 세우고(AI는 뒤에 붙임), 이후 자동화·고도화로 확장한다.

M1
기반 구축

프로젝트 셋업 & 인증

  • Next / Nest 모노레포 또는 분리 리포 구성, Prisma + PostgreSQL 연결
  • 카카오 OAuth + JWT 로그인, 사용자 생성
  • 배포 파이프라인(Vercel / Railway) 기본 구성
M2
핵심 CRUD

지원 관리 & 상태 추적

  • 지원 수동 등록 / 목록 / 상세 / 수정 / 삭제
  • 전형 단계 추가·순서·상태 토글, 전체 상태 자동 계산
  • 칸반 보드 + 대시보드 통계
M3
AI 파싱

공고 자동 분석 (링크 우선)

  • 링크 입력 → Firecrawl 수집 → Claude 구조화 파싱 → 초안 생성
  • 수집 실패·빈약 시 "본문 붙여넣기"로 자동 폴백
  • 추출 결과 보정 UI (전형 단계 편집)
M4
